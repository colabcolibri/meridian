# v2.01 — Local File Server

## Objective

Today the monitor relies on the browser's File System Access API (`showDirectoryPicker` / `input[webkitdirectory]`) to read project files. This approach has two compounding problems: every page reload silently drops the file handle, forcing the user to manually reopen the folder before any document or board state is visible, and the picker had silent failure modes that were difficult to diagnose. v2.01 replaces that mechanism with a lightweight local HTTP server that runs alongside `pnpm dev`. The user selects the project folder path once in the browser UI; that path is stored in `localStorage` and used on every subsequent load. From that point forward, F5 works, the board reloads automatically, and the path survives restarts of the dev session as long as the server is running.

## Done criteria

v2.01 is `complete` when a developer running `pnpm dev` (or equivalent) can open the monitor, enter the path to a local `docs/` folder once, and then perform a hard reload (`F5`) without any folder re-selection step — all documents and board state load automatically from the server. The local server exposes a REST endpoint that the monitor's file-reading layer calls instead of any browser file picker. No File System Access API calls remain on the hot path. The path input and persistence logic are covered by acceptance tests, and `pnpm build` exits 0.

## Explicitly out

- Any change to parsing, board derivation, or US/epic display logic — those belong to v2 and v3 respectively.
- Tauri or native file system integration (v7 / EPIC-07) — the local HTTP server is an explicit interim solution for the browser dev workflow, not the long-term native path.
- Multi-folder or multi-project support — single folder per session only.
- Authentication or security hardening of the local server — localhost-only, development use only.
