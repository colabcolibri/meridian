# US-0085 — Clickable depends_on list in Story Detail

**As** Process Manager,
**I want** to see and open each dependency user story from the Story Detail summary,
**so that** I can follow the `depends_on` chain while reviewing a story without hunting ids on the Board or in files.

## Intent

### Acceptance

- [x] When `depends_on` is non-empty, Story Detail summary shows one row per id (monospace id + title when the story exists in the loaded project), not a comma-separated line.
- [x] Tapping a loaded dependency opens a second `StoryDetailSheet` on top of the current one (`modal={false}` on the parent while the child is open), with the same summary and markdown body as a Board card click.
- [x] Closing the nested dependency sheet returns to the parent story sheet; closing the parent story sheet closes any nested dependency sheet as well.
- [x] A dependency id missing from the in-memory index renders as a disabled row with a short caption (same pattern as sprint `storyIds` in US-0083).

### Why

US-0081 moved `depends_on` out of raw YAML into the summary panel, but it still renders as plain text (`US-0080, US-0081`). That matches the old sprint deliverable UX we fixed in US-0083 for `storyIds`. When planning, the manager reads “depends on US-0080” and must leave the panel, find that card, and reopen detail — breaking the same drill-down flow we already solved for sprint commitments. This slice makes `depends_on` a first-class navigation affordance inside Story Detail only.

### Where

Follow-up in v3 / EPIC-11 after US-0081 (structured Story Detail) and US-0083 (nested sheet stack for sprint → story). Reuses `StoryDetailSheet`, `stackLayer`, and the in-memory `stories` index; no parser or `board.json` changes. Does not add reverse “blocked by” links, epic/version doc `depends_on`, or the `blocks` frontmatter field in this story.

## Plan

### Approach

- Extract shared `LinkedStoriesList` in `src/features/monitor/components/linked-stories-list.tsx` from the row markup in `SprintStoriesSummary` (`deliverable-doc-sheet.tsx`): one button per id, title from `Map(stories)`, disabled row + “Story not loaded in monitor” when missing — then use it for sprint `storyIds` and for `depends_on` in `StoryDetailSummary` with label “Depends on — tap to open detail”.
- Extend `StoryDetailSheet` to accept `stories`, `epics`, and `issues` (same inputs Board and Deliverables already have) and own `nestedDependency` state: when a dependency row is tapped, render a second `StoryDetailSheet` for that US; parent uses `modal={!nestedOpen}` and `allowOutsideDismiss={!nestedOpen}` on `MarkdownDocSheet`/`MonitorSheet` (same stacking rules as sprint → story in US-0083).
- Clear `nestedDependency` when the parent story sheet closes (`onOpenChange(false)` on the root instance) so Board and Deliverables never leave a orphan overlay; closing only the dependency sheet restores the parent story content without dismissing the sprint sheet when opened from Deliverables.
- Wire `stories` / `epics` / `issues` from `KanbanView.tsx` and from the nested `StoryDetailSheet` in `deliverable-doc-sheet.tsx` so dependency drill-down works from Board and from sprint → story without duplicating stack logic in Deliverables.
