# US-0087 — Local HTTP file server sidecar replacing File System Access API

**As** a developer using the Meridian monitor,
**I want** a local HTTP server to serve my project files over REST so the browser can read them by path,
**so that** I only need to select my docs folder once and every subsequent page reload — including a hard F5 — restores the board automatically without a folder picker.

## Intent

### Acceptance

- [x] `pnpm dev` (or an equivalent composite script) starts a local HTTP file server on a fixed localhost port alongside the Vite dev server — no manual extra step required.
- [x] A path input in the browser UI accepts an absolute folder path, persists it to `localStorage`, and is rehydrated on load so the input is pre-filled after F5.
- [x] Performing a hard reload (`F5` / `Cmd+Shift+R`) reloads all documents and board state from the server using the persisted path — no folder picker or `showDirectoryPicker` call occurs on the document-loading hot path.
- [x] `pnpm build` exits 0 and no `showDirectoryPicker` or `webkitdirectory` calls remain on the file-reading hot path.

### Why

The monitor currently uses the browser's File System Access API (`showDirectoryPicker` / `input[webkitdirectory]`) to read project files. Every page reload silently drops the file handle, forcing the user to reopen the folder before the board is visible again. This makes iterative development frustrating: a CSS fix or HMR reload is followed by a mandatory picker interaction before the real state is visible. This story replaces that mechanism with a lightweight local HTTP server sidecar. After completing this story, F5 is a productive action: the monitor reloads instantly from disk without any picker.

### Where

Opens v2.01 — the entire version is built on this foundation. There are no upstream US dependencies; all existing parsing and board-derivation logic in `app-desktop/src/` stays untouched. This US delivers the server, the path-persistence UI, and the file-reader adapter. Subsequent v2.01 work (if split) would cover architecture documentation updates (`05_architecture.md`) and any test harness infrastructure needed for the adapter layer. EPIC-02 established the folder-open contract in v0/v1; this US extends that contract to use a server transport instead of browser file picker.

## Plan

### Approach

- **Node HTTP sidecar as a Vite plugin (not a separate process).** The file server is implemented as a second Vite plugin (`meridianFileServerPlugin`) alongside the existing `meridianValidateApi()` plugin in `app-desktop/vite.config.ts`. It registers two middleware routes on Vite's `configureServer` hook — `GET /api/files?path=<absolute>` (returns raw file text) and `GET /api/list?dir=<absolute>` (returns a JSON array of filenames) — so no separate `node` process, no extra terminal tab, and no port management beyond Vite's own `server.port`. The plugin code lives at `app-desktop/vite-file-server.ts`, mirroring the existing `vite-meridian-validate.ts` pattern exactly. Both endpoints resolve paths only under the user-supplied root to prevent directory traversal; they return a 403 if the resolved path escapes the root.

- **Adapter layer in `src/features/folder/`.** A new module `app-desktop/src/features/folder/http-folder-access.ts` exports the same surface as the existing `folder-access.ts` / `ProjectFolderContext` read path (`listDir(dir: string)` and `readFile(path: string)`), but backed by `fetch('/api/list?dir=...')` and `fetch('/api/files?path=...')` instead of `FileSystemDirectoryHandle` calls. `ProjectFolderContext.tsx` gains a new provider branch: when the persisted localStorage path is present and the HTTP server responds, it calls `resolveMeridianDocsRoot` using the HTTP adapter rather than the `FileSystemDirectoryHandle` adapter, bypassing `showDirectoryPicker` entirely. The existing `FileSystemDirectoryHandle` code path is preserved and reached only when no path is stored in localStorage — this is not a removal, it is a fallback demotion.

- **Path-input UI component rendered in the WelcomeScreen / folder-open flow.** A new `PathInput` component (`app-desktop/src/features/folder/PathInput.tsx`) renders a plain `<input type="text">` with an "Open" button. It appears in the existing `WelcomeScreen` (currently shown when `status === 'none'`) as a second option below the current "Open folder" button, labelled "Enter path manually (local dev)". On submit it writes the value to `localStorage` under the key `meridian.localFolderPath` (string, shape: `{ path: string }`), then triggers the HTTP-backed folder-open flow in `ProjectFolderContext`. There is no separate settings panel — the same input is used for first-time entry and for changing the path.

- **localStorage persistence key and shape.** The key is `meridian.localFolderPath` and the value is a JSON string `{ "path": "/absolute/path/to/docs" }`. On every `ProjectFolderProvider` mount, the provider reads this key before any other branch; if a non-empty path is found and the HTTP server is reachable (a single `HEAD /api/list?dir=<path>` probe), it calls the HTTP adapter's open flow immediately — no user gesture required. This is what enables F5 to restore the board without a picker. The path is cleared from localStorage by the existing "Close folder" action already wired in `ProjectFolderContext`.

- **`pnpm build` compatibility.** The `meridianFileServerPlugin` guards all middleware registration inside `configureServer` (dev-only). In `vite build` the plugin contributes nothing to the bundle. The `fetch('/api/...')` calls inside `http-folder-access.ts` must never be reached at build time; they are only called from `ProjectFolderContext` when `import.meta.env.DEV === true`, so the build exits 0 and no server-side code is bundled. The acceptance criteria `no showDirectoryPicker on the file-reading hot path` is met because the HTTP branch short-circuits before any File System Access API call when `meridian.localFolderPath` is present.

### Out of scope for this story

- Any change to US/epic parsing, board derivation, or display logic — those belong to v2 and v3.
