# US-0110 — Board generator derives board.json from SQLite

**As** Process Manager,
**I want** `generate_board.py` to build `board.json` from SQLite user story rows,
**so that** the kanban snapshot stays derived from the canonical database without manual edits.

## Intent

### Acceptance

- [ ] New script `.agent/scripts/generate_board.py <package-root>` queries `user_stories` and writes `docs/kanban/board.json` per `board-schema.md`.
- [ ] Output fields match frontmatter mapping: `id`, `title`, `epic`, `version`, `status`, `moscow`, `depends_on` (JSON array), `done_when`, `tests`, `tests_status`, `ready`.
- [ ] Sorted ascending by US id (`US-0001` … `US-0114`).
- [ ] Dogfood: generated file card ids equal set from pre-migration `board.json` (114 cards).
- [ ] Exits non-zero if DB missing or validation fails.
- [ ] Inserts new `board_snapshots` row with `source='generate'`.

### Why

`board.json` was always derived from US frontmatter — never source of truth. With US in SQLite, the generator must read from DB or the file becomes stale immediately after `/create-us`. This preserves the Meridian rule: board is output, DB is truth. Also fulfills the architecture doc reference to `generate_board.py` that was planned since v4-S2.

### Where

**v9-S3**, depends on **US-0109** (validated DB). Works with **US-0111** (writes trigger regen). Extension `sync-board.ts` may call same Python script later — out of scope here.

## Plan

### Approach

- Create `generate_board.py` as thin CLI over `meridian_db.export_board_entries()` returning list of dicts matching `board-schema.md`; reuse field mapping from `app-desktop/src/domain/meridian/board-derive.ts` logic as reference (same column names).
- Write JSON with `json.dumps(..., indent=2)` + trailing newline to match existing `board.json` format for minimal git diff noise.
- Wire `/sync-board` workflow doc to call `python3 .agent/scripts/generate_board.py` when DB exists (documentation in US-0111; script delivered here).
